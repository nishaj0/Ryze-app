# Ryze AI and algorithms reference

This document separates deterministic training calculations from AI-assisted workflows. It is intended for contributors, reviewers, and support staff who need to explain why Ryze produced a recommendation or suggestion.

## Deterministic training calculations

| Capability | Current rule |
| --- | --- |
| Top set | Highest logged weight; repetitions break ties |
| Training volume | Sum of `weight × reps` across logged sets |
| Estimated 1RM | Epley: `weight × (1 + reps / 30)`, rounded to whole kilograms |
| Workout streak | Consecutive calendar dates with completed sessions |
| Progress history | Completed sessions with valid logged exercise sets |

These calculations use stored workout data. They are not generated by the AI model.

## Progressive-overload recommendation

The client-side helper considers valid historical sets ordered from newest to oldest. It compares the top set from the most recent session with the previous one, choosing the stronger set by weight and then reps.

For the exercise rep range:

1. If the reps are below the minimum, keep the current weight and reps.
2. If the reps are inside the range but below the maximum, keep the weight and add two reps, capped at the maximum.
3. If the reps meet or exceed the maximum, increase the load and reset reps to the minimum.

Load increments are equipment-aware:

| Equipment | Increment |
| --- | --- |
| Barbell | 2.5 kg |
| Dumbbell | 2 kg |
| Machine | 5 kg |
| Cable | 2.5 kg |
| Other/unknown | 2.5 kg |

This is an explanatory recommendation based on logged performance. Form, recovery, injury risk, and professional coaching must override it when appropriate.

## Split recommendation baseline

Onboarding’s deterministic baseline recommends:

- Full Body for beginners training three or fewer days.
- Push/Pull/Legs for intermediates training six or more days.
- Bro Split for other cases with five or more training days.

The application ranks recommendations for the user to choose from; it does not silently replace an active plan.

## Historical split-day behavior

Completed sessions persist the `splitDayId` and `splitDayName` associated with the session. Progress filters use that historical snapshot so a user can still filter old training by the day name used when it was performed, even if the active split has changed.

## Gemini platform behavior

Ryze uses Gemini for selected structured, assistant-style tasks. Calls are designed around JSON schemas and typed parsing. The integration uses a timeout and retries transient availability failures with bounded backoff. Failures must be converted into predictable application errors rather than leaking provider-specific details to users.

Structured output is still untrusted input. The API must validate exercise references, action types, and values against the app’s allowed data before using a response.

## AI Split Builder

The AI Split Builder receives profile constraints such as goal, experience, training days, available equipment, and gender. A free-text description is treated as a preference, not permission to break those constraints.

The builder filters candidate exercises from the app’s exercise catalogue and accepts only exact available exercise names. It follows current goal-oriented templates:

| Goal | Sets and reps target |
| --- | --- |
| Strength | 3–5 sets of 3–6 reps |
| Hypertrophy | 3–4 sets of 8–12 reps |
| Endurance | 2–3 sets of 15–20 reps |

It should include rest when the user does not train every day and explain conflicts between a user request and hard profile constraints.

## Coach actions

Ryze Coach can use contextual data including the current split, check-in history, recent sessions, exercise history/details, and progress summary. It can propose navigational actions, rest days, and exercise swaps.

The Coach is confirmation-only for writes: it may prepare a proposed change, but the user must explicitly confirm before a plan or schedule is changed.

## Check-ins and split suggestions

Check-ins are classified into `GOOD`, `NEUTRAL`, or `STRUGGLED` sentiment and can identify issues plus affected exercises. A repeated struggled pattern is evaluated over a configured recent window.

When eligible, the suggestion system groups recurring issues and may request a Gemini-generated proposal. Supported suggestion types are:

- `SWAP_EXERCISE`
- `REDUCE_VOLUME`
- `ADD_DELOAD`
- `ADJUST_REST`

The system respects disabled settings, active-split age requirements, and duplicate-pending protections. An eligible suggestion is always reviewable and must be accepted or dismissed by the user.

## Safety and review boundaries

- AI output is training assistance, not medical diagnosis, injury assessment, or treatment.
- User confirmation gates are product requirements, not optional UI polish.
- Recommendation quality depends on accurate, complete logs and profile data.
- Contributors must add tests when changing thresholds, recommendation rules, supported action types, or validation boundaries.
- Any new AI tool/action must have explicit authorization rules, input/output validation, an understandable user explanation, and a confirmation step for state changes.
